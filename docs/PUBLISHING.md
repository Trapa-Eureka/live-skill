## 1. Real-World Precedents — Pitfalls Already Confirmed in the Sibling Repos

Two repos by the same author (Trapa-Eureka, npm account `shiz_son`) have already walked this path. Pitfalls there is no need to go through again from scratch:

| Source | Problem | Lesson (applied to live-skill) |
|---|---|---|
| retail-mcp REL-001 | Leaving `package.json.private: true` in place makes `npm publish` itself refuse | From T0 scaffolding onward, either omit the `private` field or manage it explicitly |
| retail-mcp REL-002 | Without `bin`/`main` there is no execution entry point after `npx <pkg>` or `npm install`. Without a shebang the executable cannot run, and there was a case where entry-point detection by `import.meta.url` comparison failed when reached through a symlink | Include `bin: { "live-skill": "dist/cli/index.js" }` + shebang (`#!/usr/bin/env node`) + `chmod +x` in the build script. Test the CLI entry-point detection logic assuming it is reached via a symlink |
| retail-mcp REL-003 | If the published artifact is the `.ts` source, `tsx` is a devDependency and it cannot run in a production install. If a package actually used at runtime sits in devDependencies, an `--omit=dev` install breaks immediately | Build `dist/` with `tsconfig.build.json` and publish that; keep `tsx` as a devDependency. Before building, grep to confirm that dependencies are actually imported from core/adapters |
| retail-mcp REL-004 | Without `files`/`.npmignore`, the `.gitignore` fallback publishes every development asset (97 tests, fixtures, review docs, etc.) | Whitelist with `package.json.files = ["dist", "README.md", "LICENSE"]`. `docs/`, `samples/`, `fixtures/`, and `tests/` must never be included (directly tied to guardrails 4 and 7 as well) |
| retail-mcp REL-005 | Missing LICENSE and the `license`/`repository`/`bugs`/`homepage` metadata | LICENSE added this session. Match the `package.json` fields to the GitHub URL in T0/T11 |
| retail-mcp REL-007/QA-001~006 | Without a `prepublishOnly` gate, publishing is possible without `npm run check`. If the tests verify only the source tree and there is no smoke test of the actual tarball install, the published artifact can fail to run even with 376 tests passing | Wire it as `prepublishOnly: "npm run check && npm run verify:pack"`. Automate the tarball fresh install + `--help` smoke with a `verify:pack` script |
| retail-mcp REL-008 | npm does not clearly guarantee that an unscoped name is a "reusable unregistered name". The `@trapa-eureka` organization did not exist on npm (`npm org ls` 403), so it ended up switching to the personal-account scope `@shiz_son/retail-mcp` | `live-skill` was confirmed unregistered in this survey, but **the organization-scope problem can recur** — left as a decision item in §4 so the `@shiz_son/live-skill` alternative can be used immediately in T11 if needed |
| msg-agent `scripts/check-tarball.sh` | Automatically checks with a shell script whether `.env` or key-like strings are mixed into the `npm pack --dry-run` result (lightweight, no dependencies) | For live-skill's scale this script is a better starting point than retail-mcp's `verifyPack.ts`/`secretScan.ts` (TS, feature-rich) — recommended to port as-is and add as `scripts/check-tarball.sh` |
| retail-mcp 008 "recommended release gate" | Eight stages: clean install → check → coverage → dependency/secret audit → build → `npm pack` whitelist verification → tarball `--omit=dev` fresh-install smoke → human approval | Adding just the `verify:pack` stage to live-skill's `npm run check` (typecheck+lint+test) gives a scaled-down gate that fits the project's size (also consistent with the no-gate-relaxation principle CLAUDE.md already states — if anything, this adds one more gate) |

**The T0 scaffolding itself does not need to be designed from scratch either**: `../msg-agent` has already implemented the stack CLAUDE.md requires (TS strict + `noUncheckedIndexedAccess`, ESLint flat config + `typescript-eslint` strictTypeChecked, Prettier, Vitest + a 90% coverage threshold, `tsx`-based cli/smoke, the `check`/`prepublishOnly` script combination) up to npm publishing level. Porting `package.json`, `tsconfig.json`, `eslint.config.js`, and `vitest.config.ts` and removing only the dependencies that do not fit this repo (messaging-only ones such as grammy and franc) is faster than designing from scratch and is already proven. Its extractors (`src/adapters/extractors/{pdf,docx,text,route,limits,index}.ts`) use pdf-parse and mammoth as-is, so they serve as the direct reference implementation for T2 (however, its `extract()` returns `Result<ExtractedDoc, ExtractError>` instead of throwing, which differs from the DESIGN §2 interface, so whether to adopt that is decided in T1 — the DESIGN-diff-first principle).

## 3. npm Publishing Execution Order

1. **Finalize the package name** (human decision — WORKFLOW §4). Decide whether to go with the §0 survey result as-is (`live-skill` available) or with the `@shiz_son/live-skill` scope (§1 retail-mcp precedent), and update SPEC §8. **→ Finalized 2026-09-07: unscoped `live-skills`** (re-checked, unregistered). `name`, `bin`, `program.name()`, `verify-pack.sh`, and the README install section were changed together; the internal identifiers (role tags `[live-skill:…]`, the temporary directory prefix, the `.live-skill/` state directory convention) and the GitHub repository name are unchanged.
2. **Check the `package.json` fields**: `name`, `version` (starting at `0.1.0`), `description`, `keywords` (`agent-skills`, `claude`, `skill-compiler`, `docs-to-skill`, etc. — see the competitor keywords in MARKET.md), `license: "MIT"`, `repository`/`bugs`/`homepage` (matching the GitHub URL), `engines.node >= 22.12.0` (I2), `bin`, `main`, `type`. **Either omit the `private` field or manage it explicitly right before publishing** (§1 REL-001). *(Measured 2026-09-07: if the `bin` path is written as `./dist/…`, npm 11 warns at publish time "bin[live-skills] script name … was invalid and removed" and normalizes it by stripping the `./` — the registry manifest goes up as `dist/cli/index.js` and execution is unaffected, but to silence the warning write it without `./`, as `npm pkg fix` does. Applied right after 0.1.0.)*
3. **Finalize LICENSE**: confirm whether the copyright holder in the already-added MIT draft should be finalized as a real name/legal entity name. **→ 2026-09-07: keep the `Trapa-Eureka` notation** (unified with the sibling repos; no separate instruction to change it).
4. **English README draft** (original T11 item) — the internal `docs/` stay in Korean; add an English section at the top of the published `README.md` or split out a `README.en.md`.
5. **Publish file whitelist**: specify `package.json.files = ["dist", "README.md", "LICENSE"]` explicitly (§1 REL-004) — exclude everything else: `docs/`, `samples/`, `fixtures/`, `tests/`, `.env*`, `scripts/smoke.ts`, and so on.
6. **Check the `bin` script**: `#!/usr/bin/env node` shebang in `dist/cli/index.js`, `chmod +x` in the build script (§1 REL-002) — build only `dist/` with `tsconfig.build.json`, keep `tsx` as a devDependency (§1 REL-003).
7. **`npm run check:tarball`** (`scripts/check-tarball.ts`, H3 — SEC-012, AUD-018): checks the structured `files[].path` from `npm pack --dry-run --json` against an allowlist (`dist/**` + the package.json, LICENSE, and README* that npm always includes) and the secret/state file rules (`.env*`, config.json, `.live-skill/`, pem/key, npmrc/git), then extracts the actual tgz into a temporary directory and scans **every text file** for key patterns (sk-ant/sk-proj/AKIA/GitHub and Slack tokens/PRIVATE KEY blocks). Any command, parse, or read error is a failure (so a check that could not run never looks like a pass). The rules are pure functions in `scripts/tarballRules.ts`, so `tests/tarballRules.test.ts` verifies them with a synthetic `.env.production` and the like (the last line of defense for guardrail 7). *(The old shell script ran a regex over the human-readable `npm notice 100B .env.production` output and missed it because of the prefix and size — this replaces the msg-agent port.)*
7-1. **`npm run verify:pack`** (`scripts/verify-pack.sh`, H2 — AUD-017): installs the actual tgz into a clean temporary project with `npm install --omit=dev`, runs `live-skill --help` (the output must include `compile`) and `--version` (must match package.json), and confirms that no devDependency has slipped in (`node_modules/vitest` absent). Because it contacts the registry, it is not put into vitest (guardrail 3) and runs only as a `prepublishOnly` and CI step.
8. **`npm publish --dry-run`**: the final rehearsal, including the registry response. *(Pitfall, measured 2026-09-07: `--dry-run` hands `npm_config_dry_run=true` down to the prepublishOnly script, so the nested `npm pack` and `npm install` inside it also become dry runs, and `check:tarball` dies with "npm pack produced no .tgz" while `verify:pack` dies with an install failure. Resolved by having both scripts set `npm_config_dry_run=false` explicitly for the child npm — the first `npm pack --dry-run --json` call stays a dry run because the flag takes precedence.)*
9. **Confirm CI green — on the exact commit**: confirm that the GHA `ci.yml` (original T11 item) runs `npm run check` and passes. **While main protection does not yet exist (H1, AUD-016), this is the manual control**: for the commit SHA to be published, confirm that the CI run on the `main` branch succeeded *for that SHA* — `gh run list --branch main --commit <sha> --json conclusion,name --jq '.[] | {name, conclusion}'` must show `success` for the `check` workflow, and `git rev-parse HEAD` and `git rev-parse origin/main` must both equal that SHA (never publish from a local unpushed commit). Execution rule (current practice, CLAUDE.md "Way of working"): never push directly to main; every change goes PR → PR CI green → squash merge → re-confirm main CI on the merge commit. Since this rule is kept by humans, until the ruleset of §3-14-1 is switched on it is a "practice", not "enforcement".
10. **`prepublishOnly` gate wiring** (applied): `"prepublishOnly": "npm run check && npm run build && npm run check:tarball && npm run verify:pack"` — wherever `npm publish` is run, locally or in CI, the check, build, tarball verification, and install smoke are enforced (§1 REL-007). CI (`ci.yml`) also runs the same sequence on Node 20 and 22.
11. **Finalize the version and tagging strategy**: start semver at `0.1.0`; decide whether to use a `public beta`/`alpha` tag (`npm publish --tag beta`) according to SPEC maturity (whether the §6 success criteria are met).
12. **Confirm npm 2FA**: check the two-factor authentication of account `shiz_son` and whether an OTP is required at publish — publishing from CI requires an automation token.
13. **(Recommended) provenance publish**: `npm publish --provenance` via GitHub Actions + OIDC (the pattern retail-mcp already adopted in `.github/workflows/release.yml` — tag push → publish). Requires the `id-token: write` permission.
14. **Switch the GitHub repository to public — timing stated explicitly**: because `repository`/`bugs`/`homepage` in `package.json` point at the GitHub URL, **switch to public right before the npm publish (after confirming everything through §3-9 passes)**. Re-check immediately after switching: no traces of the private era in the README / LICENSE exposed / GitHub Actions secrets (`NPM_TOKEN`) not exposed to fork PRs. **→ Switched to public on 2026-09-07 (human). Re-check results**: no mention of being private in the README (en/ko), LICENSE (MIT, `Trapa-Eureka`) exposed at the root, 0 Actions secrets (`gh secret list` is empty) and no release workflow, so there is nothing that could be exposed to fork PRs in the first place (`ci.yml` has only `contents: read`).
14-1. **Activate the main branch protection ruleset** (H1, AUD-016 — immediately after switching to public, or on switching to the GitHub Pro plan; on the free private plan the rulesets/branch protection API returns 403 and it cannot be enabled, confirmed 2026-09-07). ## 5. Risks and Cautions

- **Guardrail 7 (secrets)**: double-check that `.env` is excluded both by `.gitignore` and by the `npm pack` whitelist. Porting msg-agent's `check-tarball.sh` is recommended (§1).
- **Guardrail 4 (copyright)**: if the `npm pack --dry-run` result includes `fixtures/docs/` or `samples/`, the `files` whitelist design was wrong to begin with (§3-5) — development assets are never published, regardless of whether the documents are self-authored.
- **Competitive crowding**: per MARKET.md §2, there are already many tools in the same category — state the "quality gate (verified generation)" differentiator in the first paragraph of the README/keywords.
- **When to re-confirm the name**: the availability survey in §0 is a 2026-09-06 snapshot. npm names are first come, first served, so re-checking right before §3-1 (final decision) is recommended.
